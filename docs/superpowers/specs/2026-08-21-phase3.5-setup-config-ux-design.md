# ConnectionWatcher Phase 3.5 — Setup & Configuration UX

**Date:** 2026-08-21
**Status:** Approved design, pending implementation plan
**Prerequisites:** Phases 1–3 + history-semantics work (all merged to master).

## 1. Purpose

Make ConnectionWatcher behave like a distributable product: it warns about
configurations that can't deliver what they promise, degrades gracefully when
they can't, sets itself up on first boot with zero typing, and gives the
administrator honest controls over its data. Also removes the worst topology-
editing pain (inserting a node into the path).

## 2. Decisions made during design review

| Topic | Decision |
|---|---|
| Settings home | New key/value `Settings` table: `Verdict.AnchorPool`, `Verdict.WeatherThreshold`, `Retention.MinuteRetentionDays`, `Retention.HourlyRetentionMonths`, `Retention.RetentionRunHourUtc`. Seeded from appsettings on first boot after upgrade (existing deployments keep behavior); DB wins thereafter. `DbPath`/debounce stay in appsettings (deployment, not configuration). |
| Wizard entry | First boot with zero targets redirects the dashboard to `/Setup`; afterwards reachable from the Config page. Purely additive — never modifies existing targets. |
| Admin scope | Retention knobs and verdict settings are editable on `/Admin`; measurement-data export stays on the backlog. |
| Danger zone | Two operations with type-the-word confirmations: Clear history (`CLEAR`) and Factory reset (`RESET`). No config-only reset (configless history is orphaned data). |
| ISP-hop discovery | Not in the wizard (TTL-2 hop is unstable, per field experience). WAN address via UPnP-IGD with a hairpin test-ping instead; the Traceroute page remains the manual tool. |
| Insert-into-path | An atomic insert-parent API primitive plus a derived "pipeline" view; no data-model change. |

## 3. Settings infrastructure (ConPersistence)

- `SettingRow { Key (PK, TEXT), Value (TEXT) }`; migration `AddSettings`.
- `SettingsStore`: typed getters/setters (string, int), `SettingsChanged`
  event wired into the existing debounced engine-rebuild path for verdict
  keys. Retention keys are read fresh by `RetentionService` at each pass.
- Seeding: at startup, any key absent from the table is populated from the
  bound appsettings value (upgrade-safe); after that the table is
  authoritative. `WatcherHostService` constructs `VerdictOptions` from the
  store; ConEngine is unchanged.
- `PUT /api/v1/settings` (validated: threshold ≥ 1, retention values sane,
  anchor pool must name an existing pool or be empty).

## 4. Config health + verdict degradation

- `ConfigHealth` evaluator (ConPersistence) returns structured warnings:
  1. No anchor pool configured → "internet weather detection is off".
  2. `Verdict.AnchorPool` names no existing pool.
  3. Anchor count < `WeatherThreshold` → "weather detection can never trigger".
  4. Anchor count < 3 → soft recommendation.
- `GET /api/v1/config/health` → `{ warnings: [{ code, message }] }`.
- UI: warning banner on all Config pages; one-line subdued hint on the
  dashboard when warnings exist.
- `VerdictCoordinator`: when determined anchors < threshold, the verdict
  detail gains the suffix "only N anchor(s) — cannot distinguish a site
  incident from internet weather". Dashboard shows "verdict off — configure
  an anchor pool" when the verdict layer is disabled.

## 5. Administration page (`/Admin`)

1. **Stats** (`GET /api/v1/admin/stats`): DB file size, row count per table,
   oldest transition/rollup timestamps, last retention run.
2. **Settings form**: retention knobs + verdict anchor-pool dropdown and
   threshold → `PUT /api/v1/settings`.
3. **Danger zone**:
   - `POST /api/v1/admin/clear-history` — deletes transitions + rollups,
     keeps config/settings, incremental VACUUM. UI confirmation: type `CLEAR`.
   - `POST /api/v1/admin/factory-reset` — wipes config, settings, history;
     reseeds built-in profiles; engine rebuilds to empty; next dashboard
     visit lands in the wizard. UI confirmation: type `RESET`.
   Both log prominently.

## 6. Quick-setup wizard (`/Setup`)

Server-rendered steps; additive only.

1. **Router** — `IGatewayDiscovery` (ConInfrastructure): host default-route
   gateway (`NetworkInterface.GetAllNetworkInterfaces()` gateway addresses)
   plus 1 s ping probes of common candidates (192.168.0.1, 192.168.1.1,
   10.0.0.1, 10.0.0.2, 192.168.100.1). Candidates shown with reachability;
   the user confirms or edits name + address (container caveat: the
   detected gateway may be a Docker bridge — that is why confirmation is
   mandatory, never silent).
2. **Anchors** — pre-checked list: Google 8.8.8.8, Cloudflare 1.1.1.1,
   Quad9 9.9.9.9, OpenDNS 208.67.222.222 (anycast resolvers built for
   public traffic; External cadence ≈ 6 pings/min each — the page says so).
3. **Router's outside (optional)** — `IWanAddressProbe`: UPnP-IGD
   `GetExternalIPAddress`; on success, test-ping the address (hairpin check)
   before offering. Failure or no reply → step explains and skips.
4. **Apply** — one transaction through ConfigService: Router (Internal
   profile) → optional Outer IP (Internal, child of Router) → selected
   anchors (External, children of the deepest path node) → pool "Internet"
   → `Verdict.AnchorPool = Internet`, threshold 2. Names that already exist
   are skipped (additive). Redirect to the dashboard.
- First-boot redirect: dashboard `OnGet` with zero configured targets →
  redirect `/Setup`.

## 7. Insert-parent + pipeline view

- `POST /api/v1/targets/insert-parent` body
  `{ newTarget: TargetDto, childIds: Guid[] }`:
  - all `childIds` must currently share the same parent (else 400);
  - creates `newTarget` under that shared parent, re-parents the children to
    it — one transaction, full `WatcherOptionsValidator` run, normal rebuild
    signal.
- **Pipeline view** on the Targets page: derived trunk = ancestor chain above
  the verdict anchor pool, rendered as stages with "insert here" buttons
  between them (opens the target form in insert mode with childIds
  prefilled); anchors render as the fan-out; LAN devices as branches off
  their trunk node. Pure presentation — no schema change; without an anchor
  pool the page falls back to the current table.

## 8. Testing

- **Unit:** SettingsStore round-trips + seeding precedence; ConfigHealth all
  four rules; insert-parent (happy path, mixed-parent rejection, validator
  rejection rollback); wizard apply service (additive skip, path chaining);
  verdict qualifier suffix.
- **Integration (WebApplicationFactory):** settings PUT → engine rebuild
  picks up new anchor pool; admin stats shape; clear-history removes rows
  and preserves config; factory-reset reseeds and first-boot redirect fires;
  setup endpoints with fake `IGatewayDiscovery`/`IWanAddressProbe`;
  insert-parent over HTTP re-parents children.
- **Page smokes:** `/Setup`, `/Admin`.
- **Vitest:** none required (wizard/admin are server-rendered; pipeline view
  is Razor).

## 9. Exit criteria

1. Factory-reset a running instance → land in the wizard → accept defaults →
   dashboard monitoring router + 4 anchors with a Healthy verdict, no typing.
2. Config page with a 1-anchor pool shows the threshold warning; the verdict
   detail carries the limited-confidence suffix; deleting the pool shows
   "weather detection off" and the dashboard hint.
3. Insert-parent slides a new "Modem" between Router and the anchors in one
   step; the pipeline view renders the new trunk.
4. Admin: retention edit persists and survives restart; CLEAR empties
   history tables (config intact); RESET returns the app to the wizard.
5. All suites green.

## 10. Out of scope

- Local-device discovery (mDNS/ARP) — backlog.
- Measurement-data export — backlog (Admin page reserves the spot).
- Traceroute-based ISP-hop discovery in the wizard — rejected as unstable;
  manual via the Traceroute page.
- Phase 4 (packaging, MQTT/HA) — next phase.
